四、工作包 A：FS-20 核心公开正文及关联失效

A1. 固定范围清单
先从 inventory 与实际 renderer 列：组件/字段、公开显示条件、数据来源、当前投影、依赖对象、更新/撤回路径、未覆盖原因。
仅补当前已有攻略核心公开正文，不新增未来组件全集。静态 route/annotation 和已修复字段先核对后复用。
媒体 alt/图注、实体 title/description 等是否纳入，以实际公开渲染和原搜索范围为准；不能因是 attachment 或内部实体表，就认定整行均公开或一概禁止。
保持非核心实时价格/库存/优惠、原始证据、管理状态、内部 ID、私有 URL、schema 原文、跟踪参数等排除边界，不以修漏搜为由全文拼接 postmeta 或 payload。

A2. 公开文本提取
优先扩展现有 WordPress 侧纯文本白名单 helper，不直接执行全部任意 shortcode 来得到搜索文本，不调用 CMS/外部实体接口，不在用户搜索时渲染全站。
公开展示不存在/依赖失效/权限不允许的字段不进入索引；隐藏注释、script/style 中的伪 shortcode 不可被解析成公开文本。
保留 legacy 合法 shortcode、单引号参数等已通过能力；不能通过覆盖文章 post_content、title、excerpt、slug、canonical 或正文事实来使关键词可搜。
先使用最小本地 fixture 复现确切漏搜，再修当前路径；必须实际 GET 检索该正文独有词，不以索引字符串出现关键词代替结果验证。

A3. 依赖与版本
沿用已有记录体系，实现能够回答“本篇公开搜索文本依赖哪些媒体/实体的哪些公开字段版本”的最小机制。
可复用现有引用/反向查找/派生记录；没有足够机制时，在前端 WordPress 侧最小补齐并记录迁移影响，不为此建设外部服务或大型独立知识库。
投影有效性至少考虑文章输入、相关依赖公开字段/公开状态、投影规则版本和实际影响渲染的能力版本。不能只看 post_modified 或只看主文章内容，而忽略关联对象变化。
文章保存、编辑引用、撤回、设密码、删除，与被依赖媒体/实体的相关变更都应准确更新/失效。只刷新相关文章，不每次搜索全库重算。

A4. 及时安全失效与重建
目标：相关业务更新成功返回后，下一次公开搜索不得仍通过已删除/撤回/不再公开的旧依赖文字命中或在摘要/计数中泄漏；新增合格文字应在明确、可验证的重建路径完成后可搜。
同步有界更新或版本校验＋失效＋有界重建均可，但不能只有“以后某天会跑 cron”而未保护失效窗口。
已失效派生内容不能继续参与命中；允许明确保留该篇仍公开的 title/excerpt 及有效部分，而不是为了失效把全部公开文章永久移出搜索。
使用队列/dirty 标记时复用本机既有能力，说明如何被推进、失败如何重试、旧结果如何被拒；不新建无限重试循环。
结果资格/有效性处理不得简单在分页取出后删卡片，造成每页数量、计数和后续页错误。总数、12 条分页、排序及公开权限一起验证。

A5. 并发与恢复
投影生成时依赖发生变化，旧生成结果不得覆盖更新结果。生成/提交及可见性规则都要可测试，不能只在 UI 列表隐藏错误行。
同一依赖被多篇引用时更新相关集合，不影响无关文章；一篇移除引用后正确移除其反向关系。
投影规则版本升级不能把旧投影静默当新版本。保存式更新和历史回填使用相同公开字段与有效性规则，不再复制第二套不一致逻辑。
在本地新建/失效/重建路径记录非秘密证据，生产如何回填仍只形成计划。

五、工作包 B：回填比较—写入窗口及生产计划安全

B1. 先复现，而不是先宣称有漏洞
读取实际回填执行器与 production-plan。确认上一轮只证明了“写入前已变化时拒绝”，还是已经存在更强的并发控制。
用可控制的暂停点安排：回填读取旧版并算投影 → 完成版本比较 → 在提交前让另一个独立应用操作保存新版或改变公开状态 → 旧回填继续提交。
另测依赖对象在窗口内改变、两个回填任务先后完成顺序反转。先记录现实现实际行为，确有缺陷再做最小修改。

B2. 安全目标与实现边界
回填仅更新搜索派生文本、有效性/依赖记录与检查点，不重保存整篇文章来触发未知写入，不改文章原文字、正式 title/excerpt、媒体、URL、发布日期和发布状态。
采用现有存储可支持且可证明的条件提交/版本保护/事务或等效机制；不要只再次读一次再无条件写入，留下同样窗口。
不强制一种跨数据库通用的 SQL 方案。说明实际 WP_SQLite_DB 与后续目标 DB 的能力、缓存和钩子边界；未在目标引擎验证就标待验，不能用兼容 db_version() 冒充 MySQL。
仅给回填进程加锁，而正常编辑/依赖更新不参加保护，不能据此宣称并发安全。
允许旧工作产物被丢弃/标 stale 并有限重新排入，但不得重新公开撤回内容；旧结果即使暂存，也不能在失效窗口参与公开查询。

B3. 中断、失败和恢复
保留既有幂等与断点成果。补验比较/提交前后中断、重复执行、失败后重试；原文和用户新编辑始终保留。
检查点只能确认实际成功且仍符合版本条件的范围；冲突跳过要单列，不能伪计完成。只处理明确 ID/版本范围，不能 posts_per_page=-1 扫库后全量写。
测试使用隔离合成数据，不能读取生产库存来生成所谓真实计划。对生产尚未知的对象数/ID明确待授权获取。

B4. 形成计划，不执行上线
更新 production-plan：当前覆盖字段、派生规则版本、回填目标条件、分批/断点/并发保护、canary、回滚或重建、激活顺序及验证。
明确未回填时旧文可搜索范围；不能部署后暗示旧文正文已全部可搜。
旧 REST 重保存脚本如果无法满足仅写派生数据和并发安全，不应作为生产执行器推荐。既有脚本原样留档，不直接删历史文件。
实际部署、生产读取与回填分别等待明确授权；本轮连“只回填一篇试试”也不执行。
