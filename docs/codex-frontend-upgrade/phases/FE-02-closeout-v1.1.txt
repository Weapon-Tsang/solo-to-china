六、FS-09：补无 JavaScript 的真实浏览器往返

1. 用实际禁用 JavaScript 的浏览器上下文连接隔离 WordPress，不用静态 HTML 或全路由 mock。
2. 从无内联搜索框的文章页点击 header 的真实搜索链接，到达可编辑搜索页；输入合法关键词并用原生 Enter/按钮提交。
3. 验证结果、第二页、阅读文章、返回、改词和无结果仍可操作。复用已有 GET/分页证据，但完整无 JS 用户链必须实际执行。
4. 优先使用现有可用的 Chromium/WebKit 能力。WebKit 自动化此前挂起，先保存错误并核查等待条件/会话，而非重复无期限等待。
5. 某引擎的自动化障碍不得直接判成产品无 JS 失效；可在另一可用引擎完成同一原生链，原引擎的未测部分单列。
   反过来，另一引擎通过也不能冒充 WebKit 完整禁 JS 链已通过。
6. 请求/DOM/截图记录显示真实 URL、表单、查询及结果；链接存在或 curl 返回 HTML 不能单独代替点击往返验收。

七、FS-25：真实错误路径，而不是把错误当成零结果

1. 在独立测试实例对搜索查询/投影读取做窄范围故障注入；走实际应用的查询错误处理分支。

3. 验证正常 0 结果与查询失败不同：前者可用 200 空态；后者使用既定适当错误 HTTP 状态（当前约定为503时验证503）、安全提示，并保留表单/重试入口。
4. 不向读者显示 SQL、表名、堆栈、凭据；不能把失败显示成“No guides found”或 0 条准确结果。
5. 撤销注入后，同一查询恢复正常。不要损坏真实数据库、删除表、改生产配置或用全站断库造成无关错误。
6. 注入开关只能用于隔离测试，不新增可由公开 query 参数开启的故障/调试后门；测试结束失效。
7. 报告实际命令、注入点、HTTP 状态、界面与恢复证据。代码中“存在错误分支”不算已测试。
